# Attack table: notes

The table is in `docs/attack-table.md` (generated by `python bench/run_attacks.py --repeat 3 --markdown docs/attack-table.md`).

## How we measured
- 3 ways of running code: **naive** (plain subprocess, no limits), **docker** (default Docker settings plus a 256 MB memory limit), **ours** (our locked box: `unshare`, user `nobody`, seccomp, resource limits).
- An attack is **CONTAINED** if its output does not contain `ATTACK_SUCCEEDED`.
- Before every runner is used, the harness runs a harmless program through it (a control check). A runner that cannot run a normal program is shown as ERROR, never as CONTAINED.
- The full run was repeated 3 times and the results were identical.
- Environment: WSL2 Ubuntu on Windows, about 2 GB of free memory during the run. Date of the final run: 12 Nov 2026.
- Attacks in this run: 15 (cpu 3, memory 3, process 3, network 3, files 3).

## Result
- naive contained 0 of 15, docker contained 9 of 15, ours contained 15 of 15.

## Honest reading
- **naive** stopped none of the attacks: CPU, memory, process and network attacks ran to the end and the file attacks read the protected file.
- **docker** stopped the 3 memory attacks (its 256 MB limit killed them, exit code 137). It did **not** stop the 3 CPU attacks or the 3 process attacks, because Docker has no CPU limit and no process limit by default. It stopped the file and network attacks only because of layout: the container cannot see the host `/tmp`, and inside the container `127.0.0.1` is not the host, so nothing was listening. That is isolation by layout, not a security feature we tested.
- **ours** stopped all 15:
  - CPU attacks: `time_limit` (CPU limit of 2 seconds).
  - Memory attacks: `memory_limit` (address-space limit of 256 MB).
  - Network attacks: `forbidden_call` (the seccomp filter killed the program when it asked for a network connection).
  - File attacks: the program runs as the user `nobody`, which cannot read the protected file (the program ends normally, with no violation).
  - Process attacks: the process limit stopped the attack (it never printed `ATTACK_SUCCEEDED`). The runner labels the run `time_limit`, because the few children that did start were still sleeping when the 5-second clock timer ended the run. In the web UI these show as Time Limit, not Policy Violation.

## Stability and a harness bug we fixed
- An earlier run gave different results for the naive runner on `net3.py`. The cause was our harness: it waited a fixed 0.5 seconds for the network listener, which was too short on a busy laptop, so the attack found nobody listening and was wrongly counted as CONTAINED. The harness now waits until port 9999 really accepts connections. After the fix all 3 runs were identical.
- The naive memory attack `mem1.py` can also change result when the computer is short of free memory, because naive has no memory limit. Close other programs before a run, and rerun if the harness warns that runs differ.

## Limits of this result
- These are 15 small attacks that we wrote ourselves, so this is evidence, not proof that the box is safe.
- Docker could be configured with CPU, process and network limits, so its column shows Docker's default behaviour only.
- The seccomp filter is a short deny-list and the C++ compile step is not filtered. See `docs/known-weaknesses.md` for the full list.
