# Attack table: notes

The table is in `docs/attack-table.md` (generated by `python bench/run_attacks.py --repeat 3 --markdown docs/attack-table.md`).

## How we measured
- 3 ways of running code: **naive** (plain subprocess, no limits), **docker** (default Docker settings plus a 256 MB memory limit), **ours** (our locked box: `unshare`, user `nobody`, seccomp, resource limits).
- An attack is **CONTAINED** if its output does not contain `ATTACK_SUCCEEDED`.
- The full run was repeated 3 times and the results were identical.
- Environment: WSL2 Ubuntu on Windows, WSL memory limit 4 GB. Date of the run:9 Nov 2026.
- Attacks in this run: 9 (cpu 3, memory 3, files 3). The network (3) and process (3) attacks will be added when they are merged.

## Result
- naive contained 0 of 9, docker contained 6 of 9, ours contained 9 of 9.

## Honest reading
- **naive** stopped none of the attacks: the CPU and memory attacks ran to the end and the file attacks read the protected file.
- **docker** stopped the memory attacks (its 256 MB limit killed them, exit code 137) but did **not** stop the three CPU attacks, because Docker has no CPU limit by default. It stopped the file attacks only because the container cannot see the host `/tmp`; that is isolation by layout, not a security feature we tested.
- **ours** stopped all 9: the CPU attacks with `time_limit` (CPU limit of 2 seconds), the memory attacks with `memory_limit` (address-space limit of 256 MB), and the file attacks because the program runs as the user `nobody`, which cannot read the file.
- **Limits of this result:** these are 9 small attacks that we wrote ourselves, so this is evidence, not proof that the box is safe. Docker could also be configured with CPU limits, so its column shows Docker's defaults only. We have not yet tested the seccomp filter through an attack (the network attacks will do that). See `docs/known-weaknesses.md` for what our box does not protect against.
